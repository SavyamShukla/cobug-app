# COBUG GitHub App setup

COBUG no longer uses a server-wide GitHub personal access token. GitHub access is user-authorized through a GitHub App. The backend stores the installation reference and creates short-lived installation access tokens when it needs to read or write a connected repository.

## 1. Create the GitHub App

GitHub → Settings → Developer settings → GitHub Apps → New GitHub App.

Recommended values for local development:

- App name: `COBUG`
- Homepage URL: `http://localhost:5173`
- **Request user authorization (OAuth) during installation: ON** (required; COBUG uses it to prove the installation belongs to the user who is connecting)
- Callback URL:
  - For Render production: `https://cobug-app.onrender.com/api/github/setup`
  - For local development: `http://localhost:8080/api/github/setup`
  *(Tip: GitHub allows adding multiple callback URLs, one per line)*
- Webhook: disabled for this first version
- Public: enable if other GitHub users will install the app

Repository permissions:

- Contents: Read and write
- Metadata: Read-only

Do not grant unrelated permissions.

GitHub Apps are preferred over legacy OAuth Apps because they provide fine-grained repository permissions and short-lived installation tokens.

## 2. Generate the private key

On the GitHub App settings page, generate a private key. Keep the `.pem` file private. Never put it in React/Vite or commit it to Git.

The `.pem` file can be used exactly as GitHub gives it (`BEGIN RSA PRIVATE KEY`). No openssl conversion is needed. The backend also accepts `BEGIN PRIVATE KEY` (PKCS#8).

Also on the GitHub App settings page, click **Generate a new client secret** and note the **Client ID**. They are used only for the ownership check described below.

## 3. Backend environment

PowerShell, before starting Spring Boot:

```powershell
$env:GITHUB_APP_ID="YOUR_GITHUB_APP_ID"
$env:GITHUB_APP_SLUG="cobug"
$env:GITHUB_APP_PRIVATE_KEY=(Get-Content "C:\path\to\your\private-key.pem" -Raw)
$env:GITHUB_APP_CLIENT_ID="YOUR_GITHUB_APP_CLIENT_ID"
$env:GITHUB_APP_CLIENT_SECRET="YOUR_GITHUB_APP_CLIENT_SECRET"
$env:COBUG_FRONTEND_URL="http://localhost:5173"
```

Then start the backend normally.

## 4. COBUG flow

Settings → GitHub → Connect GitHub → authorize/reconnect the existing installation, or install the App if it is not installed → select repositories when GitHub asks → return to COBUG.

After that, the project owner can connect one of the repositories available to the GitHub App installation. Push Main uses a fresh installation access token generated by the backend. The token is not returned to the frontend.

## 5. Installation ownership check (security)

GitHub redirects the browser to the Callback URL (`/api/github/setup`) with `installation_id`, `state` and `code`. Because `installation_id` travels through the browser, COBUG does not trust it on its own:

1. The one-time `state` ties the redirect to the COBUG user who started setup.
2. The backend exchanges `code` for a short-lived GitHub user token (used once, never stored).
3. The backend calls `GET /user/installations` with that token and accepts the connection only if `installation_id` is in the list.

If it is not in the list, the connection is refused (403). This stops someone from pasting another person's installation ID.

## 6. Desktop app behaviour

When "Connect GitHub" is clicked inside the Electron desktop app, GitHub opens in the system browser. After the user installs the app, the backend shows a small "GitHub connected, you can close this tab and return to the COBUG desktop app" page (the desktop app has no web page to redirect to). The desktop app re-checks the connection automatically when its window gets focus again, so it shows "connected" without a manual refresh. Rebuild the desktop app after updating the frontend, and restart the backend after updating Java code.

## 7. Privacy model

COBUG stores:

- the COBUG user association
- GitHub installation ID
- GitHub account ID/login
- project repository metadata

COBUG does not store:

- GitHub password
- GitHub personal access token
- GitHub client secret in the frontend
- long-lived installation access tokens

GitHub installation access tokens expire after one hour.

## 8. Connect vs. reinstall behaviour

COBUG now uses an **intelligent Connect GitHub flow** from Settings → GitHub.

When the user clicks Connect GitHub:

1. COBUG starts the GitHub App user-authorization flow.
2. If the COBUG GitHub App is already installed for that GitHub account, the backend finds that existing installation and reconnects it to the COBUG account. **The user does not need to reinstall the App.**
3. If the App is not installed, COBUG sends the user to the normal GitHub App installation page. The user then chooses which repositories the App may access.
4. After installation, the existing callback completes the connection.

Disconnecting GitHub inside COBUG only removes COBUG's stored connection record. It does **not** uninstall the GitHub App from GitHub. Therefore the next Connect GitHub action can restore the existing installation.

The project-level repository selector continues to call `/api/github/repositories`, which returns only repositories exposed by that installation. Disconnecting a repository from a project does not disconnect the GitHub account; the selector immediately returns to the available repository list.
